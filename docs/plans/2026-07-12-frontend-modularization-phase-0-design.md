# Frontend Modularization Phase 0 Design

## Overview

This document defines the foundation for frontend modularization in `apps/web/app`.

The frontend will move toward a **Screaming Architecture** organized by product capabilities, with **Hexagonal Architecture-inspired layers** inside each feature module. The goal is to make the product domain visible in the file tree, keep UI and business workflows close to their feature, and give both humans and agents a consistent rulebook when adding or modifying features.

This Phase 0 change is intentionally small. It creates the directory foundation and path aliases only. It does not migrate existing features yet.

## Changes

### Directory foundation

Create these directories under `apps/web/app/src/`:

```text
src/
├── modules/
├── shared/
└── layouts/
```

These directories prepare the application for later roadmap phases:

- `modules/` contains vertical feature modules.
- `shared/` contains cross-cutting, reusable code that is not owned by one feature.
- `layouts/` contains application and page layout composition.

`src/components/ui/` is an explicit exception because shadcn-vue is configured in `apps/web/app/components.json` to generate and read UI components from `@/components/ui`. Keep shadcn-vue managed primitives there unless the shadcn-vue configuration is intentionally changed in a dedicated task.

The existing `@/` alias remains available during migration so current imports continue to resolve.

### Path aliases

Configure these aliases in Vite and TypeScript:

```text
@modules/* -> src/modules/*
@shared/*  -> src/shared/*
@layouts/* -> src/layouts/*
@/*        -> src/*
```

Alias configuration must be present in:

- `apps/web/app/vite.config.ts`
- `apps/web/app/tsconfig.json`
- `apps/web/app/tsconfig.app.json`

Updating both TypeScript config files avoids drift between IDE tooling, Vue type-checking, Vitest, and Vite.

### Future module convention

Future feature modules should use this structure:

```text
src/modules/<feature>/
├── domain/
├── application/
├── infrastructure/
└── presentation/
```

Layer responsibilities:

| Layer | Responsibility | Examples |
| --- | --- | --- |
| `domain/` | Pure feature concepts, entities, value objects, and domain types | `media-asset.ts`, `publication.ts` |
| `application/` | Use cases, workflow orchestration, feature composables | `useComposerMediaPicker.ts`, `schedulePublication.ts` |
| `infrastructure/` | External adapters, API clients, Pinia stores, persistence details | `media-api.ts`, `media.store.ts` |
| `presentation/` | Vue views, feature components, UI-only composition | `MediaLibraryView.vue`, `components/MediaGrid.vue` |

Example future media module:

```text
src/modules/media/
├── domain/
│   └── media-asset.ts
├── application/
│   └── useComposerMediaPicker.ts
├── infrastructure/
│   ├── media-api.ts
│   └── media.store.ts
└── presentation/
    ├── MediaLibraryView.vue
    └── components/
```

### Dependency direction

Feature code should move in this direction:

```text
presentation -> application -> infrastructure -> domain
```

Practical rules:

- `presentation/` may import application services, feature stores, feature DTOs, and shared UI.
- `application/` coordinates workflows and should avoid Vue component concerns.
- `infrastructure/` owns APIs, stores, adapters, and integration details.
- `domain/` must stay framework-light and should not import Vue, Pinia, router, or HTTP clients.
- Cross-feature imports should be rare and should prefer explicit public entry points once those are introduced in later phases.
- `shared/` must not become a dumping ground. Code belongs in `shared/` only when at least two modules need it or when it is truly platform-level.

Phase 0 does not enforce these rules with tooling yet. It documents the convention and creates the import paths needed by later phases.

## Usage

### Adding a new feature module

When adding a future feature, prefer this shape:

```text
src/modules/new-feature/
├── domain/
├── application/
├── infrastructure/
└── presentation/
```

Use aliases instead of deep relative paths:

```ts
import { useMediaStore } from '@modules/media/infrastructure/media.store'
import DashboardLayout from '@layouts/DashboardLayout.vue'
import { Button } from '@/components/ui/button'
```

Use `@/components/ui/*` for shadcn-vue primitives because the project CLI configuration owns that path. Use `@shared/*` for reusable application-owned utilities or components that are not generated by shadcn-vue.

Keep existing `@/` imports working during migration, but new modularized code should prefer the more specific alias except for shadcn-vue primitives.

### Modifying existing features

When touching existing code before its module migration phase:

1. Avoid opportunistic mass moves.
2. Keep imports stable unless the issue explicitly includes migration.
3. If moving a file into `modules/<feature>/`, place it in the correct layer.
4. Update tests alongside the move.
5. Prefer focused PRs that map to the roadmap phase.

### Agent guidance

Agents working in this repository should follow these rules:

- Do not place new feature code directly under legacy `src/components`, `src/views`, `src/stores`, `src/composables`, or `src/lib` unless the task explicitly requires compatibility with unmigrated code.
- Treat `src/components/ui` as the shadcn-vue managed primitive library. Do not move it into `shared/` or `modules/` unless a dedicated task also updates `components.json` and verifies the shadcn-vue CLI workflow.
- For new feature behavior, create or use the corresponding `src/modules/<feature>/` folder.
- Keep feature-owned UI inside `presentation/`.
- Keep Pinia stores and API clients inside `infrastructure/`.
- Keep orchestration and reusable feature workflows inside `application/`.
- Keep pure types and rules inside `domain/`.
- Do not move unrelated files while implementing Phase 0.
- Run the requested frontend verification after alias changes.

## Troubleshooting

### Imports work in Vite but fail in TypeScript

Check that the alias exists in both `tsconfig.json` and `tsconfig.app.json`.

### Imports work in the IDE but fail at runtime

Check that the alias exists in `vite.config.ts` under `resolve.alias`.

### Tests fail after alias changes

Run the frontend test command from the repository root:

```bash
just frontend-test
```

If a failure mentions module resolution, compare Vite aliases and TypeScript paths.

### Lint fails because of unused aliases

Alias configuration itself should not require imports. If lint fails, inspect changed files for accidental unused imports rather than removing the aliases.
