# Exploration: Media Asset Deduplication — Content-Addressed Storage

## Summary

The codebase has a well-structured media asset system with a clean hexagonal architecture. Storage uses `shared/storage` with R2/S3-compatible providers. The current upload flow is backend-streamed (no presigned URLs), creating one physical file per asset with no deduplication. The dedup feature requires: a new `workspace_file_blobs` table, new `PENDING_UPLOAD`/`UPLOADING` states, SHA-256 computation, temp-to-canonical copy semantics, a GC job, and a frontend hash composable.

## Key Discoveries

1. **Presigned URLs are available but unused**: The `PresignableStorage` interface with `presignGet()` already exists. The dedup flow can leverage this — after dedup check, return a presigned URL for the client to upload directly to storage. This eliminates backend streaming and reduces memory pressure.

2. **Magic-byte validation is server-side only**: The `UploadAssetHandler` validates content type via magic bytes during streaming. For the dedup path, this validation needs to happen on the client (before hash) OR the server needs a separate verification step after copy.

3. **Upload slot pattern exists**: The `claimUploadSlot()` with conditional UPDATE and grace period is a good pattern to mirror for dedup — it prevents race conditions during concurrent uploads of the same hash.

4. **No existing blob dedup table**: The `workspace_file_blobs` table does not exist. The issue mentions this as the dedup layer, but it needs careful design — it must be workspace-scoped (for authorization checks) while being content-addressed (for dedup across workspaces?).

5. **Frontend already has retry logic**: The `useMediaStore` already has sophisticated retry with exponential backoff. New dedup composables should integrate cleanly with this pattern.

6. **Storage key change is breaking for preview URLs**: `AssetPreviewUrlResolver` and `MediaPreviewTokenService` use `storageKey` from `MediaAsset`. If storage keys change format, preview URL resolution must be updated — or the blob storage key must be derivable from the asset record.

7. **Delete semantics need clarification**: The issue lists `DELETED` as a state, but the current `MediaAssetRepository.delete()` hard-deletes the row. Does `DELETED` mean soft-delete on the asset, the blob, or both? Blob reference counting may be needed if multiple assets reference the same blob.

## Risks & Questions

1. **Blob reference counting**: If multiple `MediaAsset` rows reference the same SHA-256 blob, deleting one asset should NOT delete the blob. Need to determine: soft-delete blob + reference count, or blob is never deleted (simplest for MVP)?

2. **Workspace isolation for dedup**: Should identical files in different workspaces share a blob? If yes, `workspace_file_blobs` is workspace-agnostic. If no, the dedup is per-workspace (less effective but simpler).

3. **Migration of existing assets**: How to backfill SHA-256 hashes for existing `READY` assets? A one-time `MediaAssetBackfillJob` was mentioned in the issue — needs to compute hash from existing blob storage.

4. **Extension in storage key**: `sha256.{ext}` — extension is derived from MIME type. Need to map MIME → extension (e.g., `image/jpeg` → `jpg`).

5. **Client hash + server verify**: If the client sends the hash, the server MUST verify the uploaded bytes match. This requires streaming hash computation on the server side during the copy operation.

6. **Conflict between dedup fast-path and magic-byte validation**: The fast-path (hash already exists READY) skips magic-byte validation. Is this acceptable, or do we need a verification step even for deduped assets?

7. **Temp key lifecycle**: Temp keys (for client direct upload) need expiration. Should the GC job handle temp blob cleanup, or should temp blobs be in a separate prefix/path?

8. **Transaction scope**: The current `markAsReady` is a separate query after upload. For dedup, the sequence is: copy temp → verify hash → update both `workspace_file_blobs` AND `media_assets`. These need to be atomic (same transaction).
