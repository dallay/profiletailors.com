## Exploration: Bulk waitlist invitation operations (dallay/profiletailors.com#665)

### Current State
Single-entry flow exists and is the reuse target. `POST /api/admin/waitlist-entries/{entryId}/invitations` (`AdminWaitlistController.invite`, `@Transactional`) delegates to `InviteWaitlistEntryHandler.handle(InviteWaitlistEntryCommand)`, guarded by `WAITLIST_INVITE` (`PLATFORM_OWNER`/`PLATFORM_OPERATOR` only; `SUPPORT_AGENT`/`AUDITOR` denied). Eligible state is `PENDING` only: `CONVERTED` throws `WaitlistEntryAlreadyConvertedException`, `CANCELLED` throws `WaitlistEntryNotInvitableException`, `INVITED` takes a revoke-and-report path, and `PENDING` with an active legacy row throws `InvitationAlreadyActiveException`. On success the handler dual-writes legacy `WaitlistInvitation` (via `WaitlistInvitationRepository`) plus canonical `Invitation(source=WAITLIST, target=NEW_WORKSPACE, workspaceId=null)` (via `InvitationRepository.save` with `candidateKey`), transitions `WaitlistEntry.invite(now)` (`PENDING -> INVITED`, `invite()` rejects non-pending), publishes one `AdminAuditEvent(WAITLIST_ENTRY_INVITED, SUCCEEDED)` and one `InvitationIssued` domain event, and returns `AdminInvitationSummary`.

Back Office queries (#667) exist: `GET /api/admin/waitlist-entries` with `ListAdminWaitlistEntriesQuery` (`page/size/sort/status/waitlistId/waitlistKey/email/joined+invited ranges`, `ADMIN_PAGE_MAX_SIZE` guard) backed by `R2dbcAdminWaitlistQuery`, plus `GET /{entryId}` detail with invitation history. `WaitlistEntryAdmin` port (`findById/save/findInvitationContext`) is the narrow admin mutation seam over the framework-free `shared/lead-capture/waitlist` domain (`WaitlistEntry`, `WaitlistEntryStatus`, `WaitlistConsent`); `R2dbcWaitlistEntryAdmin` implements it with per-row `SELECT`/`UPDATE`. There is no bulk endpoint, no bulk command/handler, and no per-entry result type today. Auth is per-request operator resolution (`OperatorAccessResolver` + `RequestContextStore`, default-deny). Audit is per-entry (`platform_admin_audit_events`, metadata redaction at `R2dbcAdminAuditRepository.publish()`). Observability has `InvitationTelemetry`/`InvitationObservability` (created/revoked/accepted/expired/replay counters, low-cardinality tags) and `WaitlistQueryTelemetry`; raw tokens and full emails must not cross audit/log/metric boundaries per `openspec/specs/invitations/spec.md`. Admin UI (`apps/web/admin/src/views/WaitlistView.vue`) invites one entry at a time behind `platform.waitlist.invite`. BDD coverage for single invite + queries lives in `platform-admin.feature` and `platformadmin/invitations-direct.feature`. The only bulk precedent is the archived DALLAY-413 bulk-scheduling proposal (chunked 50-100, per-row errors, partial success) — explicitly out of scope as a generic framework per the issue. Referenced RFC sections 19, 20, 34, 45 were not found in-repo (no RFC document located); treated as unverified external context, not as requirements.

Dependency verification: #666 (single flow) CONFIRMED present (`InviteWaitlistEntryHandler`, `Invitation` with `InvitationTarget`, `InvitationActivationCoordinator`, single-invite BDD). #667 (Back Office queries) CONFIRMED present (`AdminWaitlistController.listEntries/getEntry`, `R2dbcAdminWaitlistQuery`, `WaitlistView.vue`). Notable drift: the archived DALLAY-570 proposal declares `WaitlistInvitation` legacy-only ("new code MUST NOT create rows"), but the live `InviteWaitlistEntryHandler` still dual-writes both tables — bulk work must decide whether to preserve or retire that dual-write, not silently extend it.

### Approaches
1. **Orchestrating bulk handler reusing the single-entry handler per entry** — new `BulkInviteWaitlistEntriesHandler` iterates validated entry IDs, calls existing single-entry logic per entry inside its own transaction boundary, catches per-entry domain exceptions (`WaitlistEntryNotFoundException`, `WaitlistEntryAlreadyConvertedException`, `WaitlistEntryNotInvitableException`, `InvitationAlreadyActiveException`, access-denied), emits per-entry audit + `InvitationIssued` on success, and returns a per-entry result list (`entryId`, `outcome: invited|skipped|failed`, `invitationId?`, `code?`).
   - Pros: zero duplication of lifecycle/invariant rules; preserves hexagonal layering (application orchestrates, domain owns invariants); per-entry auditability falls out naturally; partial success is inherent; smallest blast radius
   - Cons: N round-trips to DB (one `findById` + writes per entry); per-entry transactions need explicit demarcation (no single giant `@Transactional`); batch size must be capped to bound latency
   - Effort: Medium

2. **Single-transaction batch with pre-validation pass** — validate all entries up front (eligibility snapshot), then write all invitations + entry transitions in one transaction; any failure rolls back everything.
   - Pros: atomic all-or-nothing semantics; fewer transaction boundaries
   - Cons: contradicts the stated requirement (per-entry success/failure reporting implies partial success); a single ineligible entry blocks the whole batch; long transaction risks lock contention/timeouts on `waitlist_entries` + `invitations`; bulk-scheduling precedent explicitly rejected giant transactions in favor of chunking; audit rows would roll back with the batch, destroying the audit trail of the attempt
   - Effort: Medium (but wrong semantics)

3. **Async bulk job with persistence (`BulkImportJob`-style)** — persist a bulk job row, process entries in background chunks, expose `GET /bulk/jobs/{jobId}` for polling.
   - Pros: fits very large batches; survives client disconnect; matches DALLAY-413's async V2 sketch
   - Cons: out of scope (generic bulk framework explicitly excluded); adds tables, worker, polling, job lifecycle, and retention — an order of magnitude more surface for a Back Office operator flow that the issue describes as synchronous eligible-set invitation; no evidence the batch sizes justify it
   - Effort: High

### Recommendation
Approach 1: a synchronous orchestrating bulk handler over the existing single-entry path, with a capped batch size (propose max 50 per request, aligned with the 50-100 chunk precedent from DALLAY-413 and the existing `ADMIN_PAGE_MAX_SIZE` guard philosophy), per-entry transaction boundaries (each entry commits or fails independently), per-entry audit events (success → `WAITLIST_ENTRY_INVITED/SUCCEEDED`; ineligible → same action with `REJECTED` + stable code; unexpected → `FAILED`), one `InvitationIssued` per success only, HTTP 200 with a per-entry result envelope plus a summary (`requested/succeeded/failed/skipped`), and HTTP 207 left explicitly undecided for the proposal phase. Reuse `WAITLIST_INVITE` permission with a single up-front check (fail-fast 403 before touching any entry). Resolve the `WaitlistInvitation` dual-write drift in the proposal: either bulk preserves dual-write for parity (documented as legacy debt) or single + bulk both stop writing it (separate migration decision) — do not let bulk silently diverge from single. No campaign segmentation, no scoring, no generic bulk framework, no new permission, no schema change anticipated (verify unique-index behavior on `invitations.source_reference_id` active-WAITLIST rows under concurrency in design).

### Risks
- Dual-write drift: live handler still writes legacy `waitlist_invitations` despite the archived 570 proposal forbidding it; bulk must not entrench or silently fork this — needs an explicit proposal decision
- Partial-failure audit completeness: per-entry audit writes must not share the entry's transaction or they roll back on failure; each entry's audit + state change needs a defined commit boundary
- `INVITED`-state re-entry semantics: single flow revokes-and-reports on `INVITED`; bulk must define whether `INVITED` entries are `skipped` (safe default) or re-invited, and the proposal must pick one
- Batch-size and timeout abuse: uncapped lists risk long requests and token-generation storms (`InvitationTokenGenerator` + `TokenHasher` per entry); a hard cap + request validation is mandatory
- Token/secret leakage in bulk responses and events: bulk result must carry invitation IDs and status codes only — never raw tokens; `InvitationIssued.rawToken` handling must stay on the DALLAY-565/566 path
- Idempotency/retry: operator retry of a partially-successful batch must be safe (already-invited entries become deterministic `skipped`, not duplicates or errors); needs a stated retry contract
- RFC sections 19/20/34/45 not found in-repo: any requirement attributed to them is unverified until the orchestrator supplies the document
- Concurrent bulk vs single invite on the same entry: conditional-transition guards (`updateIfVersionMatches`, active-invitation checks) must hold under contention; needs a concurrency BDD case

### Ready for Proposal
Yes — dependencies verified present, reuse seam identified (`InviteWaitlistEntryHandler` + `WaitlistEntryAdmin` + existing query filters), and the recommended approach fits hexagonal/DDD rules with no invented APIs. The orchestrator should tell the user: (a) confirm batch cap (proposed 50) and `INVITED`-entry semantics (proposed `skipped`), (b) decide the dual-write question, (c) supply the RFC doc if sections 19/20/34/45 contain binding requirements, then proceed to `sdd-propose` for `dallay-665-bulk-waitlist-invitation`.
